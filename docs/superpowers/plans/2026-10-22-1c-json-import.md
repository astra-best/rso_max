# Импорт вложенной выгрузки 1С в JSON

## Критерии и дизайн

- Админ-страница принимает только `.txt` с UTF-8 JSON-массивом; upload/request body ограничены единым `MAX_CONTENT_LENGTH` (по умолчанию 128 MiB, настраивается окружением). Существующий `database.import_from_excel` остаётся для совместимости со старыми данными.
- JSON читается как `PersonalAccount → MeteringPoints → Meters → Scales → TariffZones`. Внутренние integer PK/FK остаются отдельными от внешних ID 1С.
- Пустые номера ЛС пропускаются. Если нормализованный номер ЛС встречается в выгрузке более одного раза, пропускаются все ЛС с этим номером (вместе с поддеревом). Существующие счета обновляются по `number` (только `one_c_id`); ФИО и адрес в выгрузке 1С отсутствуют, из JSON не читаются, существующие `fio`/`address` не изменяются.
- Добавляются сущности точек учёта и приборов, дочерние таблицы шкал/тарифных зон. Точка учёта принадлежит ровно одному ЛС: прямой FK `metering_points.licschet_id` (без таблицы связей); при повторной выгрузке `licschet_id` обновляется, если 1С перенесла точку на другой ЛС. Целиком отклоняется только файл, который нельзя обработать (не UTF-8, невалидный JSON, корень не массив). Остальные некорректные элементы (ЛС, точка, прибор, шкала, зона) пропускаются вместе с поддеревом с WARNING в логе (причина, JSON-путь, GUID 1С, номер ЛС): отсутствие ID (нет поля, пустая строка или пустая ссылка 1С `00000000-0000-0000-0000-000000000000`) или ID не в формате GUID (не строка, иной формат, пробелы по краям — без обрезки), текстовые поля не строкой, пустой/некорректный номер ЛС, повтор `PersonalAccountID`, `PersonalAccountID`, закреплённый в БД за другим номером, повтор `MeteringPointID` (точка остаётся за первым ЛС), повтор `MeterID` (остаётся первое вхождение), пустой `MeterNumber`, вложенные поля не-массивы. Импорт выполняется в одной транзакции; неожиданная ошибка откатывает всё. Результат: количества ЛС/точек/приборов/шкал/зон и число пропущенных элементов.
- Upsert сохраняет сущности и связи, отсутствующие в новой выгрузке. JSON не добавляет строки в `pokazaniya`. Текущие `schetchiki` и показания сохраняются миграцией и продолжают обслуживаться legacy-путём.
- Предоставленный пример выгрузки содержит повторяющиеся номера ЛС, `MeteringPointID` и `MeterID`; такие элементы пропускаются с записью в лог, остальное импортируется. Файл не модифицировать и не копировать в тесты.
- Синтетический генератор ограничен максимумом 1000 ЛС; поддерживает негативный режим с повторным `MeterID`. Первый DB-прогон — максимум 100 ЛС; до большего объёма требуется отдельное разрешение владельца.
- Текущий HTTP importer читает максимум 128 MiB и полностью разбирает JSON в памяти; он не подходит для предполагаемых 600 000 ЛС. Линейная оценка sample-файла около 358 MB превышает лимит. Это блокирующее ограничение: до заявлений/использования такого объёма нужны streaming/staging importer, корректная атомарность и отдельный разрешённый volume test. Первую проверку не увеличивать выше 100 ЛС.

## План реализации

1. Тестами зафиксировать атомарный импорт вложенной структуры, внешние ID отдельно от PK/FK, принадлежность точки учёта одному ЛС, пропуск и логирование некорректных элементов, неизменность ФИО/адреса, отсутствие удалений и показаний, откат при неожиданной ошибке, а также сохранность legacy-данных при `init_db`.
2. Добавить аддитивную схему в `database.init_db`, JSON-парсер (разбор файла до `BEGIN IMMEDIATE`) и импортёр с поэлементной валидацией внутри транзакции; обновить `get_schetchiki`, чтобы runtime видел JSON-приборы вместе с legacy-записями без удаления старых строк.
3. Переключить `/upload` и шаблон на `.txt` JSON, обновить HTTP-тесты для отказа `.xlsx` и успешного/ошибочного JSON.
4. Добавить генератор JSON до 1000 ЛС; проверить синтетический импорт не более чем 100 ЛС и пропуск повторного `MeterID` в негативном наборе. Перед большим DB-прогоном запросить разрешение владельца.
5. Запустить связанные тесты и статические проверки, доступные в среде; передать стабильный diff координатору для независимого ревью/тестирования.

## Область файлов

- `database.py`: аддитивная схема, атомарный importer, чтение новых приборов.
- `web.py`, `templates/upload.html`: только новый формат админ-загрузки.
- `tests/test_database_1c.py`, `tests/test_main_fixes.py` и/или отдельный `tests/test_1c_json_import.py`: содержательные тесты поведения и формы.
- `scripts/generate_synthetic_1c_json.py`: ограниченный синтетический набор.
